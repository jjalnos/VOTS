# Cloudways staging and production handoff

These instructions deliberately omit database passwords, API keys, MFA tokens, and media credentials. In the Cloudways Velocity environment editor, mark runtime secrets **Sensitive**; Cloudways documents that their values are hidden after saving and cannot be viewed again. Treat this as runtime environment delivery, not as a claimed full secrets vault. Google Cloud Secret Manager is the production source of truth for versioning and rotation. Never copy secret values into repository files, build logs, tickets, or chat. Follow the [security and secrets handoff](SECRETS_HANDOFF.md).

## Staging

1. Create a dedicated staging Node.js application and use the Cloudways native PostgreSQL connection already provisioned for that application. Do not reuse a production database or superuser.
2. In Cloudways deployment settings, select **Next.js SSR**, **npm**, Node.js 20.9+, build command `npm run build`, and entry command `npx next start`. Cloudways performs the dependency-install step separately.
3. Store the authoritative version of every secret in Google Cloud Secret Manager, then project the pinned staging version into Cloudways using its Sensitive option. A saved Sensitive value is hidden and cannot be viewed again; removal is still possible. Compose `DATABASE_URL` from Cloudways’ generated host, port, database, username, and password. Do not commit or paste those values into tickets or chat. Set `DATABASE_SSL` to the mode Cloudways documents for the internal connection.
4. Set `DATA_ADAPTER=postgres`, `AUTH_PROVIDER=database`, `DEV_AUTH_ENABLED=false`, `STAFF_MFA_REQUIRED=false`, independent random `AUTH_SESSION_SECRET` and `PASSWORD_RESET_TOKEN_KEY` values of at least 32 bytes, the exact HTTPS `NEXT_PUBLIC_SITE_URL`, and `NEXT_PUBLIC_COMING_SOON=true` until museum acceptance. The temporary MFA bypass affects staff only; passwords, active-account checks, and role permissions remain enforced. The site URL is also the trusted origin for authenticated writes and the sole origin allowed in emailed recovery links. An explicitly selected PostgreSQL adapter fails closed; it does not fall back to fixtures.
5. Before production, set `STAFF_MFA_REQUIRED=true` and configure `MFA_PROVIDER=webhook`, an HTTPS `MFA_VERIFY_URL`, and its Sensitive bearer token. The hook receives only `{ userId, providerReference, code }` and must return `{ "verified": true }` for success. Family contributors do not call the MFA hook. Turning the flag on rejects staff sessions created while MFA was bypassed.
6. The Git-only Velocity deployment can run reviewed migrations at process startup: set `DATABASE_AUTO_MIGRATE=true` only after taking a backup. `src/instrumentation.ts` runs the checked-in Drizzle migration journal while holding a PostgreSQL session advisory lock across migration and bootstrap; request handlers never issue archive schema DDL. Do not run migration generation on the server.
7. For the empty Robin demo database, set `BOOTSTRAP_CONFIRM=CREATE_INITIAL_ROBIN_CURATOR` together with Sensitive `BOOTSTRAP_CURATOR_PASSWORD` (16+ characters), `BOOTSTRAP_CURATOR_EMAIL`, and `BOOTSTRAP_CURATOR_DISPLAY_NAME`. The same startup pass creates one dual admin/curator identity after migrations. It becomes an idempotent no-op for that exact identity and refuses to add an owner to a non-empty unrelated database. After the first successful login, remove every `BOOTSTRAP_*` variable and redeploy so the plaintext bootstrap password does not remain in the process environment. The preview account created with `STAFF_MFA_REQUIRED=false` must later go through a separate audited MFA enrollment/update before that flag is turned on; merely adding a reference to bootstrap variables will not mutate an existing identity. The separate `npm run auth:bootstrap-admin` command remains available for hosts with one-off shell access.
   - For an exceptional controlled credential handoff, the same exact dual-role identity can be assigned a new password only while all normal bootstrap inputs are present, `BOOTSTRAP_ROTATE_PASSWORD_CONFIRM=ROTATE_INITIAL_ROBIN_CURATOR_PASSWORD`, and `BOOTSTRAP_ROTATION_ID` is a fresh UUID v4. That UUID durably claims the one-time operation through the audit-event primary key, so retained environment values cannot replay after a later password change. The transaction verifies the target and roles and writes a system audit event without recording the password or its hash. Verify the new login, then remove the rotation confirmation, operation ID, `BOOTSTRAP_CONFIRM`, every `BOOTSTRAP_CURATOR_*` value (including password and MFA reference), and any legacy `BOOTSTRAP_ADMIN_*` values; redeploy immediately.
   - To add one administrator/curator to an already populated database, first take a database backup and confirm an active account already holds both roles. Generate a new UUID v4 for this operation. In Cloudways, set `PROVISION_ADMIN_CURATOR_CONFIRM=PROVISION_ADDITIONAL_ADMIN_CURATOR`, `PROVISION_ADMIN_CURATOR_OPERATION_ID` to that UUID, `PROVISION_ADMIN_CURATOR_EMAIL`, `PROVISION_ADMIN_CURATOR_DISPLAY_NAME`, and a Sensitive `PROVISION_ADMIN_CURATOR_PASSWORD` of 20–200 characters. When `STAFF_MFA_REQUIRED=true`, also set `PROVISION_ADMIN_CURATOR_MFA_REFERENCE` to the target's enrolled provider reference before deploying. Keep `DATABASE_AUTO_MIGRATE=true` for this startup pass. The operation creates an active dual-role identity and a system-operator audit event in one transaction; it refuses an existing email, a missing active dual-role owner, a reused operation ID, or any attempt to change an existing password. After the deployment succeeds, verify the new account can log in (including MFA when enabled). Then remove **every** `PROVISION_ADMIN_CURATOR_*` variable from Cloudways and redeploy immediately; do not leave the confirmation, operation ID, password, identity fields, or MFA reference in the runtime environment.
8. Configure the self-hosted internal AI endpoint on a private network path. `LOCAL_AI_ALLOWED_HOSTS` is required and must contain its exact hostname (without scheme, path, wildcard, or port); even loopback must be listed. A missing or nonmatching allowlist selects the deterministic fallback and the network boundary rechecks it before every request. Do not make the endpoint public without authentication, network controls, logging policy, and resource limits. The internal provider always rejects OpenAI/ChatGPT/Codex-owned and Azure OpenAI hostnames.
9. Leave external OpenAI research disabled until the museum approves source policy, data handling, budget, and model configuration. To enable it, set `EXTERNAL_AI_USAGE_STORE=auto` (or `postgres`), both external-provider switches, the model/key, every `EXTERNAL_AI_*_LIMIT`, and a complete usage-alert provider configuration. For Cloudways Elastic Email use `EXTERNAL_AI_USAGE_ALERT_PROVIDER=smtp` and the SMTP settings below. The existing Resend option remains available with `EXTERNAL_AI_USAGE_ALERT_PROVIDER=resend`, a Sensitive `RESEND_API_KEY`, and a verified `EXTERNAL_AI_USAGE_ALERT_FROM`. Both adapters require `EXTERNAL_AI_USAGE_ALERT_TO=support@clicksmith.net`. Missing or invalid accounting/alert configuration blocks the call. The UI must obtain per-request paid-search consent and send both `confirmed: true` and the exact `costAcknowledgement: "CLICKSMITH_PAYS_OPENAI_FEES"`; the server rejects either field if it is missing or altered. Never persist, prefill, or silently reuse this acknowledgement. OpenAI requests are non-stored (`store: false`), limited to one web-search tool call, and capped by `EXTERNAL_AI_MAX_OUTPUT_TOKENS`.
10. Checked-in migration `0002_external_ai_usage_governance` creates the three minimal `external_ai_usage_*` tables. The ledger also verifies them defensively with idempotent DDL. Reservations, daily/monthly checks, and alert dedupe are atomic/durable in PostgreSQL. Expired unsettled reservations are atomically converted into `provider-error` usage records charged at the full reserved ceiling; they are not deleted from accounting, including when a provider response succeeded but settlement failed. Confirm those tables and a limit-denial test in staging before setting `OPENAI_EXTERNAL_RESEARCH_ENABLED=true`. Without a reachable durable ledger, paid research fails closed; `demo_memory` can report demo status but cannot authorize a live OpenAI call.
11. The Robin Archive Intake accepts one original per request, at most 8 MiB, so multipart overhead stays below Cloudways' commonly documented 10 MiB upstream default. Metadata, ciphertext, audit event, quota, and idempotency rows commit in one PostgreSQL transaction. Store the AES-256-GCM master key as a versioned Secret Manager secret and project the selected value into a Cloudways Sensitive variable. The current demo runtime resolves only one key even though each blob records a key-version number, so do not rotate in place until a multi-version resolver or verified re-encryption migration exists. Retain every key version required by live ciphertext or backups. Every original begins quarantined. The separately invoked curator/MFA-only limited text review can clear only a validated UTF-8 `.txt`/`.md` original of at most 500,000 bytes after authenticated decryption, checksum verification, strict decoding, and NUL/control/bidirectional-control checks; its transition and reviewer are committed in the same transaction as a durable audit event. It is not antivirus. CSV, PDF, office, image, audio, and video originals remain quarantined and unavailable until a separately governed production malware scanner marks them clear.

## Cloudways Elastic Email SMTP

Before enabling password recovery or SMTP alerts, add and activate Elastic Email for the intended Cloudways application. In Elastic Email, verify `voicesoftheshoah.org` and publish every DNS record the provider requires for sender authentication. An MX record is not required for this outbound-only sender; do not invent or replace inbound-mail routing merely to turn that optional status indicator green. Do not send from the domain until SPF, DKIM, tracking, and DMARC are verified. The approved envelope/header sender for this application is `no-reply@voicesoftheshoah.org`.

Set these server-side Cloudways environment variables exactly for the normal Elastic Email STARTTLS connection:

| Variable | Value or source | Handling |
| --- | --- | --- |
| `SMTP_HOST` | `smtp.elasticemail.com` | Non-secret; the application rejects every other host. |
| `SMTP_PORT` | `2525` | Non-secret. |
| `SMTP_SECURE` | `false` | Starts as SMTP and upgrades with STARTTLS; this is not plaintext delivery. |
| `SMTP_REQUIRE_TLS` | `true` | Required so delivery fails if STARTTLS cannot be established. |
| `SMTP_USER` | Dedicated `vots-smtp-<unique>@voicesoftheshoah.org` SMTP-credential username | Create the credential before publishing its exact username; project it as **Sensitive**. |
| `SMTP_PASSWORD` | Password generated for that dedicated SMTP credential | Store the authoritative value in Secret Manager and project it as **Sensitive**. Do not reuse the Cloudways account-wide API key. |
| `SMTP_FROM` | `no-reply@voicesoftheshoah.org` | Must belong to the verified sender domain. |

Create a dedicated Elastic Email SMTP credential for VOTS instead of copying the account-wide Cloudways API key used by other bindings. Elastic Email shows the credential password only once. Use a globally unique username matching `vots-smtp-<8-to-32-character-unique-suffix>@voicesoftheshoah.org`, and give it only SMTP sending capability. Do not commit or announce the exact username before the credential exists. Do not add an IP restriction unless Cloudways confirms a stable Velocity egress range.

Also set `EXTERNAL_AI_USAGE_ALERT_PROVIDER=smtp` and keep `EXTERNAL_AI_USAGE_ALERT_TO=support@clicksmith.net`. None of the SMTP variables may use a `NEXT_PUBLIC_` prefix. The application requires every SMTP value; pins the host, port, STARTTLS mode, and sender shown above; rejects malformed credentials and messages; enforces certificate verification; and uses bounded connection and socket timeouts. It does not fall back to Resend or another provider when SMTP is selected. After saving Sensitive values, Cloudways will not display them again; retain the pinned Secret Manager version and rotate by projecting a new version rather than attempting to recover the saved value.

Before cutover, take an on-demand Cloudways backup and record the current deployed commit and alert-provider setting as the rollback point. Deploy the backward-compatible SMTP code first while paid external research remains disabled and without changing the current alert provider. Smoke-test that release. Then add the complete SMTP variable set, switch `EXTERNAL_AI_USAGE_ALERT_PROVIDER` to `smtp` in the same Cloudways save, and redeploy. Exercise the usage-alert path in staging with the exact dedicated Nodemailer credential before enabling paid external research; Cloudways' server-level test may use a different account credential and is not a substitute. Confirm receipt at `support@clicksmith.net` and inspect the received message's authentication results. If the build, health check, SMTP verification, or message test fails, restore the recorded provider setting and previous deployment immediately, keeping paid research disabled. Do not print credentials, full environment output, SMTP exception objects, or provider responses while testing. After the rollback window, remove and revoke any dormant Resend credential.

The initial DMARC policy may use `p=none` only as a monitoring phase. After all legitimate senders are inventoried and received messages show aligned SPF and DKIM, approve a staged move to `p=quarantine` and then `p=reject`; consider changing SPF from `~all` to `-all` only after the same inventory. Do not tighten either policy blindly, because it applies to every legitimate sender for the domain.

## Production

Use a separate production application, PostgreSQL database/user, storage location, Secret Manager secrets, internal AI instance, and audit/job infrastructure. Use a dedicated least-privilege workload identity for direct Secret Manager access: Google recommends an attached service account on Google Cloud or Workload Identity Federation for an external workload; do not assume Cloudways provides a compatible federated identity without validating it. Grant Secret Accessor on individual secrets, not the whole project. Pin numeric secret versions for releases and follow the rotation, rollback, archive-key retention, client-exposure, and logging controls in the [security and secrets handoff](SECRETS_HANDOFF.md).

Enable Cloudways backups and confirm restore procedures, including a database restore plus archive-decryption test with retained key versions. Terminate TLS at the platform, set the canonical `NEXT_PUBLIC_SITE_URL`, set `STAFF_MFA_REQUIRED=true`, validate the MFA hook, security headers, and cookies, disable the coming-soon flag only after curatorial acceptance, and run the complete verification suite against the release candidate.

Official references: [Cloudways Velocity environment variables](https://support.cloudways.com/en/articles/15550368-how-to-launch-a-velocity-application-on-cloudways), [Secret Manager best practices](https://cloud.google.com/secret-manager/docs/best-practices), [Secret Manager authentication](https://cloud.google.com/secret-manager/docs/authentication), and [Secret Manager access control](https://cloud.google.com/secret-manager/docs/access-control). Never export Cloudways credentials to repository files.
